## A. Why the previous build was recoverable

The previous `print("Hello World!")` build was scanner-clean, but a restricted runtime still recovered `Hello World!`. Its constant path had one index-based `D(i)` router into sharded pool slices, one `W()` word decoder, one `NODE`/`ARG` reconstruction path, and one `EVAL`/`EXEC` handler-table dispatch structure. Chunk getters reconstructed each encoded blob, metadata parsed slice records centrally, and a runtime hook on the print environment or a focused decoder/dispatcher could observe decoded values as the VM used them. A clean intermediate representation was not shipped, but the shape of the recovery path was stable across builds. The program must execute, so observing its print output is unavoidable; the fix removes the single obvious hook and clean IR shortcut, not runtime observability itself.

## C. Substantive hardening

- Every build chooses one of three VM profiles, a bank count, group counts/coefficients, handler groups, opcode maps, per-node operand coefficients, node layout, dispatch style, router style, chunk plan, word order and stream order. Five builds have distinct structural digests and payload layouts.
- There is no `D(i)` that returns an arbitrary constant, no central `W(i)`, `NODE(n)`, `EVAL(n, fr)` or `EXEC(n, fr)` router, and no central `DEC` table. Constants, pool bytes, instruction bytes, words, nodes and dispatch steps are split into independently guarded group functions.
- Group functions require capability tickets generated by fresh call-site closures; enumerating one table with index values alone returns defaults. Slice and fragment selectors require a chained ticket from the previous decoder stage.
- Source constants are deliberately spread across pool slices, constant banks/groups and byte groups. The encoded provenance header is gone; no build id, private map, comment, brand, debug output or plaintext source fragment is emitted.
- Operands are reconstructed with a per-node permutation derived from the logical node index. Opaque NOP padding, nested blocks and branch inversion change control flow without changing evaluation order.
- Handler tables are split into per-build groups keyed by random 32-bit opcodes. Existing lazy chunk assembly, rotated byte-by-byte string reconstruction and randomized rolling checksums remain; new type/count checks verify generated helper groups without destructive behavior, persistence, credential access or abusive anti-debugging.
- These are obfuscation encodings, not encryption and not a security boundary. No unsupported Roblox APIs or non-Luau features are used.

## F. Remaining limitations

A client-side Luau script cannot be made impossible to reverse engineer. An analyst who can execute or debug the script can hook `print`, standard library functions, executor-specific callbacks, local calls, closures and upvalues; decoded constants become visible when the VM uses them. The ticket/group layout slows trivial dump hooks and removes a clean intermediate representation, but a full debugger or patient static analysis can still recover behavior. Tools under `tools/` are official Luau 0.747, not a certification of any Roblox executor. There is no red-team benchmark, commercial superiority claim or 100% decompile-proof claim. Real security needs server-side authority. Deployment remains local-only: no remote, push, GitHub repository or Render service was created.
